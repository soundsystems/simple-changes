## Group work into units

A focused unit describes one user-visible outcome. Group by behavior,
dependency, data boundary, ownership, and independently verifiable value, not by
file count, directory convenience, or commit count.

For each unit record:

- stable ID and plain-language title;
- outcome;
- exact relative paths;
- source checkout/branch;
- dependencies and merge order;
- exclusions and preserved paths;
- proportionate checks;
- release impact;
- counterpart-surface parity dispositions when the repository defines related
  clients, roles, locales, interfaces, or SDKs;
- required authority and proposed operations.

Every changed path must appear exactly once across units, preserved concurrent
work, paused work, or explicit exclusions. Reject duplicates, missing paths,
absolute paths, `..` traversal, paths outside the canonical checkout, and
symlinks.
When the same relative path is changed in multiple worktrees, bind an exclusion
to both `worktreePath` and `path`; never force the user to exclude every source
with that filename.

For Ship, bind this conserved plan, generated from the current inventory, to
the active loop with `loop record-scope`. The resulting pre-ship scope is a
runtime gate, not optional narration: guarded mutation and completion fail
until it exists. Treat lease role `preserved` only as deletion protection;
classify that work's paths independently as included, deliberately preserved,
or explicitly excluded in the plan.

Prefer one unit when changes share an outcome and must ship together. Split when
they are independently valuable or carry distinct review, data, ownership, or
deployment risk. Make dependencies explicit instead of combining unrelated
work.

When deterministic grouping cannot infer a meaningful outcome, it may propose a
conservative unit and say why. A model may refine the plan, but the bundled
validator still owns path conservation and authority enforcement.

When `package.json` or a dependency lockfile changes, include a frozen install
and production build from an isolated clean checkout. A successful build using
an existing local dependency cache does not prove a clean deployment install.

After review/integration, record one exact shipment-outcome receipt with `loop
record-outcome`. A delivered or target-equivalent unit must match its immutable
opening source result. Review-driven source changes require a fresh scope;
controller-authored outcome data never proves independent review. One exception
covers work packaged from a dirty primary checkout and reviewed elsewhere: a
delivered unit sourced from the primary may bind the reviewed target result
instead of its opening bytes, but only while that primary is unchanged from its
baseline and its HEAD is contained in the bound target. Bind every
scoped unit to exact final tree entries, including deletions, owned rename
originals, and gitlinks. Account for every remaining path generated by release
reconciliation or added by external target movement as a short
`release-generated` or `external-target-change` entry. Completion rechecks
the exact entries and refuses an omitted unit, wrong blob/mode/gitlink, moved
target, or unreported final-target delta. The controller records this receipt;
it adds no user approval step, and existing cleanup safety remains unchanged.
This controller audit step is not another user decision.

Start from a draft instead of writing the receipt by hand:

```sh
simple-changes loop draft-outcome --run-id <run> \
  [--changelog-receipt prepared.json] --output outcome.json
```

It only reads the lease and Git, with no lock and no write besides `--output`,
which refuses an input under any name and any path inside the Git common
directory, where the lease lives. Git runs with the same read-only settings
as `simple-changes status` (see `inventory-and-concurrency.md`), and an object
it cannot read stops the draft instead of turning a file into a deletion.
It binds the current target, lists every path changed on the target since loop
start with its exact `ls-tree` entry (`null` for a deleted or moved-away path),
pre-fills each scoped unit's final paths and rename originals, and adds the
rest as `additionalPaths`: `release-generated` when the changelog receipt's
`paths` names the path, otherwise `external-target-change`. A unit is
suggested as `delivered` when a scoped path changed on the target during the
run and `target-equivalent` when none did. Path movement alone proves
neither, so the draft warns, naming the paths, when a unit's final target entry
differs from the opening source result its scope recorded, which
`loop record-outcome` refuses unless a reviewed primary result or an approved
preserved-source override covers it. Every reason, unit summary, and
evidence item is a `SIMPLE-CHANGES-DRAFT:` placeholder that names the commits
that touched the path, and the draft carries a `draftReview` field. These are
drafts, not findings: review each classification and disposition, replace
every placeholder with the reviewed reason, delete `draftReview`, then run
`loop record-outcome`, which refuses a receipt that still has `draftReview` or
any placeholder marker and rechecks every entry. No runtime's schema accepts
`draftReview`, so even an empty draft (no scoped units and no target change)
and an older runtime refuse the draft until it is reviewed; only 0.28.0 and
later also refuse a leftover marker. The draft never suggests a disposition
for a [held unit](#held-unit): it leaves the unit out of `units`, warns that
it is held, and when the target changed one of its paths, it attributes that
change to the other unit that scopes the same filename or lists it as an
`external-target-change` whose placeholder says the filename match does not
show the held unit shipped.

## Preserved-source override

A second exception is a user-approved escape hatch, not a routine path. It
covers a claimed author's dirty checkout whose work reached the target in an
independently reviewed, semantically equivalent but not byte-identical form,
while that checkout itself stays preserved. Use it only when an independent
reviewer, neither the controller nor the author, has compared the source and
target results, and the user has explicitly approved keeping that checkout.
Never use it to skip review, to excuse different behavior, or for the primary
checkout.

Record the unit as `target-equivalent` with a `preservedSourceOverride` object
that binds: `runId`, `unitId`, the author's `claimId`, `sourceWorktree`,
`sourceBranch`, `sourceHeadRevision`, and `sourceChangeDigest`; the bound
`targetRevision`; `paths` with each scoped path's opening `sourceEntry` and final
`targetEntry`; `decision: "semantically-equivalent"`, `reviewerAgentId`,
`reviewReference`, and `reviewedAt`; and the user's `approvedBy`,
`approvalReference`, `approvalReason`, and `approvedAt`. Restate the approval on
the command; the flags must match every override in the receipt and are refused
when the receipt has none:

```sh
simple-changes loop record-outcome --run-id <run> --agent-id <controller> \
  --receipt <file> --approved-by <user> --approval-reference <reference>
```

Recording requires a dirty, actively claimed, non-primary author checkout still
at its frozen branch, head, and status digest, with no rename originals, whose
claim and owner are unchanged; every scoped path covered exactly once, with
unchanged source bytes and the exact target entries; a reviewer who is neither
the controller nor the author; and an approval given after the review, by
someone other than either, no more than one hour before recording.
The runtime keeps the overrides out of the lease, in
`<common-git-dir>/simple-changes/preserved-source-override/<run-id>.json`, so
older clients can still read the lease; that file is left in place afterward
as audit evidence, and `evals/schemas/preserved-source-override.schema.json`
defines it. The recorded outcome digest is the digest of the complete receipt
you submitted, overrides included, so editing any override field, such as the
approver, reference, reviewer, or a path entry, or removing the file, no longer
matches it. `loop finalize` and `loop end` recheck all of it under the
coordination lock. The run closes with that checkout and its claim untouched
only while nothing moved: any later source, claim, or target change, or an
override file that no longer matches the recorded digest, blocks completion. The override records review and approval
evidence; it never substitutes for them. Finish, end, or archive a run that
recorded an override only with Simple Changes 0.25.0 or later: an older runtime
still reads its lease but ignores the override file, so it cannot enforce these
checks.

## Held unit

A frozen scope cannot reclassify a unit, and an outcome may report a scoped
unit only as `delivered` or `target-equivalent`. When a scoped unit is
deliberately kept out of this shipment, for example because independent review
found defects, neither is true: path movement such as a shared changelog edit
does not show that it shipped, and a path absent from the target does not make
it equivalent. Hold it instead:

```sh
simple-changes loop hold-unit --run-id <run> --agent-id <controller> \
  --unit <unit ID> --reason <why> \
  --readiness-evidence "<unit ID>: <the failed-readiness evidence>"
```

Without approval flags the command changes nothing. It prints the exact state
it observed and its digest: the unit and its paths, the source checkout,
branch, head, status digest, and each path's current and opening entry, the
active claim and its owner, the target revision, the reason, and the cited
evidence. Show that observation to the user and ask now. A hold needs the
user's fresh approval of that exact observation; an earlier conditional
instruction, such as "hold it if review finds defects", never stands in for
it. After the user approves, run the printed command with `--approved-by
<user> --approval-reference <where they approved> --observation-digest
<digest>`. The command observes again under the loop and coordination locks
and refuses when anything in the observation changed, so a moved source head,
changed status or bytes, a changed claim, or a moved target needs a new
approval. The approver must be neither the controller nor the claim owner.

Attribution is declared, never inferred from filenames: each
`--readiness-evidence` item must start with the held unit's exact ID and a
colon, then state the evidence, and must not name another scoped unit's ID.
A filename, especially a shared one such as a changelog, does not say which
unit failed. The command also
refuses a unit whose exact opening bytes are already in the target at every
path (record it as delivered or target-equivalent), a unit that is not in
the frozen scope, a unit already held, a unit that a scoped unit that is not
held depends on, a missing source checkout, and a run that already recorded
its outcome: a hold never reinterprets a recorded outcome.
Genuinely new scope still needs a new shipment run or an approved replan.

The hold is immutable and lives beside the lease in
`<common-git-dir>/simple-changes/held-units/<run-id>.json`, defined by
`evals/schemas/held-units.schema.json`. It keeps the original unit exactly as
the frozen scope recorded it, the approved observation and its digest, the
authorization, and the unit's paths as exclusions bound to its source
checkout, so the frozen scope still accounts for every original path once
per checkout: delivered, preserved, or excluded, even when another checkout
changes the same filename. Any edit to the record, a record from another run,
or one that no longer matches the frozen unit fails closed. Each hold also
writes an immutable event to the run's history,
`<common-git-dir>/simple-changes/history/<run-id>/held-unit-<hold digest>.json`,
and events and holds must match both ways, so removing, replacing, or adding
to the record by hand, before or after the outcome, stops all automatic
cleanup and blocks completion; a recorded hold whose approver is the
controller or the claim owner fails the same way. The held source head is pinned at
`refs/simple-changes/held/<run-id>/<unit ID>`, which is kept afterward, so no
branch deletion, by this runtime or an older one, can leave the held commit
unreachable.

`loop record-outcome` then refuses the held unit in `units` and no longer
requires it; account for any of its paths the target changed as
`additionalPaths`. Finalization never removes, demotes, or releases a held
unit's source checkout or claim, keeps that claim even when someone else
removed the checkout, never deletes its branch, and never
switches, fast-forwards, or normalizes a primary checkout a held unit was
packaged from, clean or not. A held primary path counts as excluded
in the primary delivery proof, and so does the original path of a held
rename, so the other units can still verify delivery. A run that held every
unit, with an exactly empty outcome because the target did not move, closes
with its held work in place and `deliveryStatus: unverified`.
A unit that shares a non-primary checkout with a held unit cannot be verified
delivered while the held bytes keep that checkout dirty. The finalization
receipt reports each held unit under `heldUnits`, apart from verified
delivery, with whether its source still matches the hold.

Holding a unit is the one change to a run's lease. The first hold adds a
`heldUnits` key holding the digest of every hold, and each later hold updates
it. A run without holds keeps its lease and its outcome digest exactly as
before, so earlier runs, receipts, and frozen scopes read as they always did.
The key only makes older readers refuse: runtimes before 0.33.0 validate the
lease strictly, so once a run holds a unit, every older command that reads
the active lease refuses it, including `loop status`, `loop verify`, `loop
record-outcome`, `loop finalize`, `loop end`, `loop archive-recorded`, and the
worktree commands that check the active loop. An older runtime therefore
cannot record an outcome over a held run, report it delivered, clean it up,
or release a held checkout's claim through finalization. This runtime refuses
a lease whose key disagrees with the held-unit record, including a key that
was removed. The outcome digest the lease records also binds every hold, so
adding, removing, or changing a hold after the outcome blocks completion, and
finalization checks the record, the lease key, and that digest before any
cleanup. The sidecar, the history events, and the pinned refs stay the
source of truth; use Simple Changes 0.33.0 or later for every step of a run
that held a unit.
